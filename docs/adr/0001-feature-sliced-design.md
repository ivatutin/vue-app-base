# 0001. Feature-Sliced Design как основная архитектура

- **Status:** accepted
- **Date:** 2026-05-22

## Context

Проект — стартовый шаблон, рассчитанный на рост в полноценное B2B-SPA с 30+ страницами, командой 3+ разработчиков и горизонтом развития 2+ года.

Базовые подходы к организации кода во Vue-проектах:

1. **Плоская структура** (`components/`, `views/`, `stores/`, `utils/`) — стандарт Vue CLI / Vite-шаблонов. Работает до 20-30 файлов, дальше превращается в свалку: невозможно понять зависимости, тяжело удалять фичи, разработчики постоянно сталкиваются на merge'ах.
2. **Модули по фичам** (`modules/users/`, `modules/orders/`) — лучше, но без формальных правил импортов модули начинают зависеть друг от друга по принципу «удобно сейчас», и через год получаем граф вместо дерева.
3. **Feature-Sliced Design** ([feature-sliced.design](https://feature-sliced.design)) — индустриальный стандарт для крупных React/Vue/Angular приложений: формальные слои с правилом одностороннего импорта, сегментная конвенция внутри слайса, публичный API через `index.ts`.

Команда: один опытный разработчик, ожидается рост. Нужен подход, который **масштабируется** при добавлении людей и при этом **не overkill** для текущего размера.

## Decision

Принимаем **Feature-Sliced Design** как основную архитектуру проекта. Слои:

```
shared  →  entities  →  features  →  widgets  →  pages  →  app
                                                 processes ─┘
```

Правила:

1. Импорт **только из нижних** слоёв. Соседние слайсы того же слоя не импортируют друг друга.
2. Каждый слайс имеет публичный API через `index.ts` (barrel). Прямые импорты внутрь слайса запрещены.
3. Сегментная конвенция внутри слайса: `ui / model / api / lib / schema`.
4. `features/` — зарезервирован, наполняется по мере роста.
5. Cross-entity сценарии живут в `processes/`, а не в сторах сущностей.

## Consequences

### Положительные

- **Предсказуемая навигация** — любой код находится быстро по правилу «что это: shared утилита? бизнес-сущность? UI-блок? сценарий?».
- **Удаление фич без сюрпризов** — высокоуровневые слои всегда «верхние», удаление слайса не оставляет осиротевших зависимостей.
- **Параллельная разработка** — разработчики реже конфликтуют на одних и тех же файлах: каждый работает в своём слайсе.
- **Готовность к масштабированию** — `shared/` потенциально выносится в npm-пакет, FSD-структура переживает рост до десятков сущностей.

### Отрицательные

- **Кривая обучения** для тех, кто не сталкивался с FSD — нужны ADR и [architecture.md](../architecture.md).
- **Overhead на маленьких задачах** — даже однострочный хелпер требует решения, какой слой/сегмент.
- **Дисциплина импортов** держится либо людьми, либо ESLint-правилами. Без автомата деградирует к 3-му месяцу команды → плановое внедрение `eslint-plugin-boundaries` в [ROADMAP](../../ROADMAP.md), Фаза 2.

### Что меняется в коде

- Структура `src/` следует слоям FSD (уже сделано).
- Каждый слайс отдаёт публичный API через `index.ts` (уже сделано).
- Сегменты `ui / model / api / lib / schema` внутри слайса (уже сделано).

## Альтернативы (для истории)

- **Плоская структура** — отклонена: проект не выживет масштаб.
- **Модули по фичам без формальных слоёв** — отклонены: нет защиты от деградации структуры.
- **Hexagonal / Clean Architecture в чистом виде** — overkill для SPA с одним bounded context.
