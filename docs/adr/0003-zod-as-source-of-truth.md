# 0003. Zod как источник истины для типов

- **Status:** accepted
- **Date:** 2026-05-22

## Context

Domain-модели в SPA нужны в трёх контекстах одновременно:

1. **TypeScript-типы** — для статической проверки.
2. **Валидация ответа API** — backend может прислать что угодно (особенно при ошибках, миграциях, старых клиентах).
3. **Валидация форм** — пользовательский ввод не доверяется.

Подходы:

1. **Параллельные определения.** Отдельно `interface User`, отдельно валидация форм (Yup/Vuelidate), отдельно валидация ответов API (либо никак). Самое популярное, но ломается на любой правке поля: TS-тип говорит одно, валидация — другое, API возвращает третье.

2. **TS-типы как источник истины + runtime validators.** Например, `io-ts`, `runtypes`. Лучше, но всё равно требует синхронизировать два мира (TS-типы и schema-определения).

3. **Schema-first.** Один источник истины — Zod-схема. TS-тип выводится через `z.infer<typeof schema>`. Один объект описывает структуру, ограничения, и автоматически валидирует.

Проект уже использует Zod 4. Нужно зафиксировать его как **единственный** источник типов для domain-моделей.

## Decision

Все domain-модели (`User`, `Permission`, `Phone`, …) описываются как Zod-схемы. TS-типы выводятся через `z.infer<typeof schema>`. Параллельные `interface`/`type`-определения для тех же сущностей **запрещены**.

```ts
// src/entities/user/schema/user.schema.ts
export const userSchema = z.object({
  id: z.uuid(),
  fullName: z.string().max(31).trim(),
  // ...
})

export type User = z.infer<typeof userSchema>
```

Любой ответ от backend проходит `safeParse` перед попаданием в стор:

```ts
const res = userSchema.safeParse(rawResponse)
if (!res.success) return Promise.reject(res.error)
return res.data
```

Brand-types применяются для значений, требующих обязательной валидации:

```ts
export const phoneSchema = z.string()
  .transform(normalizePhone)
  .refine((v) => E164_REGEX.test(v))
  .brand<'Phone'>()
```

## Consequences

### Положительные

- **Один источник истины.** Любая правка поля → одно изменение → синхронны все три контекста.
- **Runtime-защита от грязного backend.** Сломал контракт — упало в одном понятном месте с понятной ошибкой, а не размазалось `undefined`'ом по UI.
- **Бесплатная типизация forms.** Тот же `userSchema` (или его partial) валидирует форму регистрации.
- **Brand-types.** Невозможно случайно передать произвольную строку туда, где ждут провалидированный `Phone`.
- **Composability.** Схемы комбинируются (`.merge`, `.extend`, `.pick`, `.omit`), что упрощает создание DTO-вариантов одной модели.

### Отрицательные

- **Накладной расход на runtime-валидацию.** Минимальный, но не нулевой. Для горячих путей (большие списки на 10k+ элементов) — стоит измерять.
- **Привязка к Zod.** Миграция на другой validator (если потребуется) — переписывание всех схем. Митигация: схемы изолированы в `schema/`-сегменте, миграция остаётся локальной.
- **Соблазн смешать API-контракт и domain-модель.** Если backend возвращает snake_case, а UI хочет camelCase — нельзя описывать это одной схемой. Решение зафиксировано в [ADR-0005](0005-dto-domain-mapping.md): для каждой сущности с API — три файла (`<x>.dto.ts` + `<x>.schema.ts` + `<x>.mapper.ts`), DTO дальше `api/`-сегмента не выходит.

### Что меняется в коде

- `entities/user/schema/user.schema.ts` — уже использует подход; камелКейс-фикс выполняется в рамках [ADR-0005](0005-dto-domain-mapping.md) (см. также [KNOWN-ISSUES.md](../../KNOWN-ISSUES.md), пункт 1).
- `shared/model/phone/phone.schema.ts` — пример brand-type.
- Новые сущности — обязательно через Zod.

## Альтернативы (для истории)

- **Параллельные `interface` + Yup** — отклонено: рассинхронизация неизбежна.
- **io-ts** — рассмотрено, отклонено: менее эргономичный API, меньше adoption, чем у Zod.
- **TypeScript-only без runtime-валидации** — отклонено: нет защиты от грязного backend и от пользовательского ввода.
