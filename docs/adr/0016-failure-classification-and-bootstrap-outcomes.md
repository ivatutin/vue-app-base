# 0016. Классификация отказов и исходы bootstrap

- **Status:** accepted
- **Date:** 2026-07-21
- **Revision:** 2 (2026-10-16) — добавлено правило для **не**идемпотентных auth-вызовов (таймаут не ретраится; бэкенд может довести операцию после обрыва) и таймаут на конкретный запрос (`RequestOptions.timeoutMs`, 60 с у `sign-up/phone`).

## Context

Приложение стартует в мире, где API может быть недоступен: сеть отвалилась, бэкенд деплоится, БД лежит, мобильный оператор держит соединение в чёрной дыре. До этого решения любой сбой на старте сводился к одному состоянию `failed`, а `failed` не имел ветки в `App.vue` — пользователь видел **вечный прелоадер**. Ошибка при этом попадала в notification-стор, но `<AppNotifications/>` рендерится внутри layout'а, то есть внутри `<router-view>`, которого при `!isReady` нет. Показать её было физически нечем.

Смежная проблема: `HttpClient` не имел таймаута, а reject `fetch` уходил наверх сырым `TypeError: Failed to fetch`. Из-за этого (а) недоступность была неотличима от «медленно» и навсегда вешала single-flight refresh-мьютекс, (б) рвались все проверки `instanceof HttpError` вверх по стеку, (в) в UI утекал англоязычный текст браузера.

Отдельный вопрос — **чем** проверять доступность. Напрашивается preflight-пинг `/health` перед стартом, но он отвечает на вопрос «был ли сервер жив секунду назад», а нужен ответ на «может ли приложение работать сейчас»: health вернёт 200, а следующий `/users/me` упадёт. Плюс лишний round-trip на каждом холодном старте.

## Decision

1. **Доступность выводится из реального запроса, а не из пинга.** Когда сессия есть, `GET /users/me` **и есть** проверка доступности — она проверяет ровно тот путь, который нужен приложению. Отдельный preflight не вводим. Для анонимного случая (реального запроса нет) `/health` уместен, но **неблокирующим** баннером на странице логина — отдельной задачей, не здесь.

2. **Единый классификатор причин отказа** — [shared/api/failure.ts](../../src/shared/api/failure.ts):

   | kind | источник | retryable |
   |---|---|---|
   | `offline` | транспорт упал при `navigator.onLine === false` | да |
   | `network` | reject `fetch`: DNS, отказ соединения, CORS | да |
   | `timeout` | `AbortSignal.timeout` | да |
   | `server` | 5xx (включая 503 «БД лежит» от `/health`) | да |
   | `auth` | 401/403 после неудачного refresh | — не отказ |
   | `contract` | провал Zod-разбора ответа | нет |
   | `unknown` | прочие 4xx и всё неопознанное | нет |

   `navigator.onLine` используется только в отрицании: `false` почти наверняка значит «сети нет», `true` не гарантирует ничего.

3. **Таймаут — предусловие, а не опция.** `HttpClient` получает дефолтный `timeoutMs: 30_000` (`0` отключает), reject `fetch` оборачивается в `HttpError` со `status: 0`. Отмена, инициированная вызывающим кодом, пробрасывается **как есть** — caller должен уметь отличить «я сам отменил» от «сеть упала».

4. **Bootstrap принимает три решения, а не два:**
   - **сессии нет или она истекла (401)** → `ready`. Это нормальный путь: guard уведёт на login. Экран ошибки здесь был бы враньём.
   - **retryable** → два тихих повтора (0.5 c, 2 c), затем `failed` с `retryable: true`. Тихие повторы переживают короткий сетевой сбой, и пользователь о проблеме не узнаёт.
   - **`contract` / `unknown`** → `failed` с `retryable: false`, без кнопки «Повторить».

   `BootstrapError` расширен до `{ message, kind, retryable, technical }`. `message` — для пользователя, `technical` — для `<details>` и логов.

5. **Guard ждёт восстановления сессии** через внедряемый `waitForSession` (`whenSessionRestored()` из `processes/app-bootstrap`). Первая навигация стартует синхронно внутри `app.use(router)`, то есть до bootstrap; реактивности `storeToRefs` недостаточно, потому что `beforeEach` не перезапускается задним числом.

   Два инварианта, которые легко сломать:
   - **сигнал разрешается до `router.isReady()`** — иначе guard ждёт bootstrap, а bootstrap ждёт `isReady()`, и это дедлок. «Сессия восстановлена» и «bootstrap завершён» — два разных события;
   - **при retryable-отказе сигнал остаётся неразрешённым** — успешный повтор обязан перезапустить guard с уже восстановленным состоянием, иначе пользователь окажется на логине при живой сессии.

6. **Экран отказа — самодостаточный виджет** [widgets/app-bootstrap-error](../../src/widgets/app-bootstrap-error/). Рендерится вне `<router-view>`, поэтому ни layout, ни snackbar, ни навигация ему недоступны. Авто-повтор с нарастающей паузой 10/30/60 c, мгновенный повтор по событию `online` и при возврате во вкладку.

7. **Таймаут **не**идемпотентного вызова — не повод повторять.** Живой факт (16.10.2026): `sign-up/phone` на холодном
   CIBA-минте занял >30 с, клиент оборвал запрос по таймауту, **а бэкенд операцию довёл** (в логе
   `Provisioned local user … (active)` + `request aborted, responseTime 30640`). Отсюда правило:

   - ретраить можно только **идемпотентные** вызовы — чтения (`GET /users/me` → `retryOn404`, повторы bootstrap);
   - `sign-up/email` и `sign-up/phone` — **без автоматического повтора**: повтор той же регистрации вернёт
     `409 ContactAlreadyExists` про **свой же** только что созданный аккаунт;
   - UI на таймаут этих вызовов говорит «не дождались ответа» и предлагает **войти** (аккаунт мог быть создан);
   - окно ожидания расширяется точечно: `RequestOptions.timeoutMs` у `sign-up/phone` — 60 с (холодный путь ~30 с,
     тёплый ~6.5 с); клиентский дефолт остаётся 30 с.

   Список неидемпотентных вызовов фиксируется **здесь**, а не «по памяти»: ошибка классификации даёт либо дубль
   операции, либо застрявшего пользователя.

## Consequences

- **+** Недоступность API стала наблюдаемой: вместо вечного прелоадера — экран с причиной и повтором.
- **+** Приложение восстанавливается само. Реакция на `online` — одна строка, но именно она превращает «вышел из метро» в «приложение уже работает» вместо «пользователь тыкает кнопку».
- **+** Протухшая сессия больше не выглядит как отказ сервиса и корректно ведёт на login.
- **+** Классификатор общий: тот же `classifyFailure` пригоден для рантайм-деградации и для UI-обработки ошибок форм.
- **+** Таймаут закрывает дедлок refresh-мьютекса при повисшем соединении.
- **−** Тихие повторы удлиняют худший случай холодного старта на ~2.5 c до появления экрана ошибки. Осознанный размен: короткие сбои гасятся незаметно.
- **−** `AbortSignal.any` ещё на границе baseline (Safari 17.4, Firefox 124) — оставлен feature-detect с ручным фолбэком. Убрать, когда поднимем целевые браузеры.
- **−** Анонимный случай пока не покрыт: при лежащем бэкенде пользователь узнаёт об этом только при сабмите формы логина. Закрывается неблокирующим health-баннером — отдельная задача.
- **−** `App.vue` удерживает экран ошибки на время повтора (не сменяет прелоадером), чтобы не размонтировать виджет и не сбрасывать счётчик backoff. Неочевидно; при рефакторинге легко сломать.

Дополняет [ADR-0006](0006-fetch-based-http-client.md) (HTTP-клиент) и [ADR-0012](0012-error-coding-contract.md) (реестр бизнес-кодов ошибок): ADR-0012 отвечает на «что за бизнес-ошибка вернулась», ADR-0016 — на «состоялся ли запрос вообще и можно ли повторить».
